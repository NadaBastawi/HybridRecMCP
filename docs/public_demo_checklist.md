# Public demonstration checklist

Run these checks on the actual hosted URL before sending it to an employer or client.
Local checks do not establish public availability. Leave unchecked until observed.

- [ ] Public URL opens in a private browser without a developer login or local tools.
- [ ] Desktop and mobile layouts render, including input labels and full card text.
- [ ] Ohio is selectable; Tucson and Ohio are clearly independent examples.
- [ ] New synthetic customer works with Unknown history (no invented service date).
- [ ] Known interval and existing synthetic customer produce recommendations.
- [ ] Five relevance-ranked service ideas include service-specific context and a staff question.
- [ ] Priority is explained separately; unknown history shows unknown priority.
- [ ] Changing region, scenario or profile details clears old results.
- [ ] Invalid ZIP/input produces a helpful message without a traceback.
- [ ] GitHub footer link opens the correct repository; Nada Bastawi is identified.
- [ ] Synthetic data, illustrative prices and independent-project disclaimers are visible.
- [ ] No keys, environment values, real customer records or administrative controls appear.
- [ ] Cold/wake startup and subsequent interactions take acceptable time for the meeting.
- [ ] No Streamlit error is visible; rehearse again after a hosting reboot/update.

## 60–90 second business demonstration

**0–15s:** “I'm Nada Bastawi. This independent proof of concept explores how staff
could review relevant service ideas consistently. Profiles, prices and priority labels
are simulated; this is not a company system.”

**15–40s:** Select Ohio if appropriate, New customer, a house profile and Unknown
service timing. Generate recommendations. Read the actual top card's context and staff
question. “This gives staff a starting point for a conversation. It doesn't diagnose
an infestation or authorize treatment.”

**40–65s:** Switch to Existing synthetic customer and generate again. “The list is
ranked by estimated relevance. Priority is a separate illustrative follow-up signal.
Staff confirm observations and suitability before deciding what to discuss.”

**65–90s:** Point to the disclosures and developer/GitHub footer. “The next useful
step would be to review the service workflow and rules with staff, then agree on how
to evaluate a small authorized pilot.” Offer engineering details separately; the
main presentation need not explain SVD, training or MCP.
